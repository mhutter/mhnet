# PostgreSQL

On rhea, PostgreSQL 18 from `services/postgresql.nix`; on the fleet, the
`postgresql` role ([Fleet](#fleet)). Both back up dumps, not the live cluster
(`docs/backup.md`).

rhea's cluster lives on `/nix/persist` and listens on the Unix socket
`/run/postgresql` and on localhost only. Per-app `pg_hba.conf` rules are
generated by that module and land above the nixpkgs defaults, which are
otherwise left as they are.

## rhea: app databases

Each app gets one role and one database **sharing the app's name**, with the
role owning the database. Declare it next to the rest of the app's config:

```nix
mhnet.postgresql.apps.<name> = {
  passwordFile = null;  # null => peer auth only
  localhostTCP = false; # also allow 127.0.0.1 + ::1
};
```

`pg_hba.conf` is first-match-wins and does **not** fall through to the next rule
when authentication fails, so an app is either peer or password — never both.
That gives three cases:

| Case                  | Declaration                                             | Connects as                                           |
| --------------------- | ------------------------------------------------------- | ----------------------------------------------------- |
| Peer over the socket  | `apps.foo = { };`                                       | system user `foo`, no password, via `/run/postgresql` |
| Password, socket only | `apps.foo.passwordFile = …;`                            | any local process holding the password                |
| Password over TCP     | `apps.foo = { passwordFile = …; localhostTCP = true; }` | the above, plus `host=127.0.0.1 port=5432`            |

Peer is the default because it needs no secret. Reach for a password when the
app connects over TCP (a JDBC URL, a container on the host netns) or runs under
a system user with a different name.

### Adding a peer app

```nix
mhnet.postgresql.apps.myapp = { };
```

That is all — but a system user named `myapp` must exist, otherwise peer auth
has nothing to match.

### Adding a password app

1. Add the secret to `secrets.nix`: `"secrets/pg-myapp.age".publicKeys = hostRhea;`
   — the key is the path `agenix` is invoked with, relative to `secrets.nix`.
2. Create it: `agenix -e secrets/pg-myapp.age` (run inside `nix develop` / direnv)
3. Declare it and point the app at it:

   ```nix
   age.secrets.pg-myapp.file = ../secrets/pg-myapp.age;

   mhnet.postgresql.apps.myapp = {
     passwordFile = config.age.secrets.pg-myapp.path;
     localhostTCP = true; # only if the app cannot use the socket
   };
   ```

4. `just switch`

Rotating is the same minus the setup: `agenix -e secrets/pg-myapp.age` and
`just switch`. The password is (re-)applied on every boot and activation by a
`postgresql-password-myapp.service` oneshot, which runs after the roles exist
and before `postgresql.target`. Order dependent services `after =
[ "postgresql.target" ]` and they will find a usable password.

The secret never reaches the nix store: systemd reads it via `LoadCredential=`
and hands it to `psql` through the environment and psql's own `\getenv`, so it
also stays out of `ps` output and the unit file.

## Verifying

```sh
sudo -u postgres psql -c '\l'                  # database exists, owner == role
sudo -u myapp psql -d myapp -c 'select 1'      # peer app
systemctl status postgresql-password-myapp     # password app, active (exited)
PGPASSWORD=$(sudo cat /run/agenix/pg-myapp) \
  psql -h 127.0.0.1 -U myapp -d myapp -c 'select 1'
```

## Gotchas

- **Nothing is ever dropped.** Removing an app from `apps` stops managing its
  role and database but leaves both in the cluster. Clean up with `DROP DATABASE`
  / `DROP ROLE` by hand.
- **Adding a `passwordFile` removes peer auth** for that app on the socket. Give
  the app its password in the same change, or it will stop connecting.
- **The nixpkgs fallback rules use `md5`.** Managed apps never reach them — our
  `scram-sha-256` rules sit above — but anything not declared in `apps` that
  connects over 127.0.0.1 hits `host all all 127.0.0.1/32 md5`. In practice that
  still negotiates SCRAM, since `password_encryption` defaults to
  `scram-sha-256`; it only weakens if a role is ever given an md5-format
  password by hand.

## Fleet

The `postgresql` role installs the server from apt; app roles include it and
create their database:

```yaml
- name: Install PostgreSQL
  ansible.builtin.include_role:
    name: postgresql

- name: Create my-app database
  ansible.builtin.include_role:
    name: postgresql
    tasks_from: database
  vars:
    postgresql_database_name: myapp
```

The owning role defaults to the database name (`postgresql_database_owner`) and
gets no password: the app runs as a matching system user and connects over the
socket via Debian's default `local all all peer` rule.

Tuning goes to `conf.d/10-tuning.conf`, sized from the host's RAM:
`shared_buffers` 20% (not the usual 25% — the app is the other large consumer),
`effective_cache_size` 50%, `maintenance_work_mem` 5% capped at 256 MB,
`max_connections = 20`, SSD-appropriate planner costs. Every value is a
`postgresql_*` variable overridable per host; `postgresql_extra_settings`
appends anything else. A change restarts PostgreSQL, briefly taking the app's
database down.
